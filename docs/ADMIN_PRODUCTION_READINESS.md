All 36 pre-existing application tables retained their row counts. No production database was accessed.

**Workflow evidence.** Using an ordinary staff credentials sign-in and a running app backed by synthetic data, two concurrent retail confirmations produced one invoice job and a single verified payment. After a pack-size change, two concurrent cancellations returned the original 400 g once. A training payment was reviewed by its individual ID and the seat moved to Confirmed. Separate keyboard and viewport checks covered 320, 390, 768 and 1440 px. Screenshots in this section contain synthetic customer and staff data.

**Regression checks.** The combined admin, payments, order pricing, inventory, catalog, editorial and shop run passed 204 tests in 19 suites. A separate cart, checkout, UPI and shipping run passed 54 tests in five suites. The runs overlap. The repository-wide Jest command still reports failures in the legacy checkout flow, wishlist and chat suites. The standalone order/invoice script also exits when Jest discovers it. A green full-repository run remains outstanding.

**Optimized build and signed-in walkthrough.** The production build passed with fresh generated Prisma types and produced 95 prerendered pages. In the built app over local HTTPS, a signed-out order link passed its original search filter to the sign-in page. A signed-in operator at 390 px opened Today and followed Ready to pack to the confirmed-order queue. ### Deploying this version

1. Back up the target database, restore it to an isolated instance, apply the migrations there, and compare record counts. In the deployment pipeline run `npm run db:release` against the intended database as a distinct release step, followed by the application rollout. The reconstructed schema preserves historical columns. Review older payment discrepancies with the person who checks the bank before making any financial correction.
2. Configure the hosting scheduler and `CRON_SECRET`. The configured jobs worker runs every five minutes and the news import runs daily. For another scheduler use the same authenticated endpoints. Point an uptime monitor at `/api/admin/operations-health` with the scheduler credential. A failed job or a payment older than the configured `STAFF_PAYMENT_ALERT_MINUTES` returns 503. Assign finance the payment alert, fulfillment the stock queue, and the site owner the failed job queue.
3. Verify the production SMTP and invoice storage credentials with a controlled order. Check that the stored invoice is readable and a failed notification can be retried. SMTP can acknowledge a delivery just before a worker stops. A retry uses a stable Message-ID, but delivery guarantees depend on the recipient's mail system. Review legacy files at the hosting layer if any receipts were previously served publicly.
4. For managed staff sign-in, link an owner’s verified Google Workspace account, enforce MFA in that Workspace, then configure `STAFF_AUTH_MODE=managed-google` and `STAFF_GOOGLE_DOMAIN` for the exact domain. Test owner recovery and revocation before enabling it in production. This setup requires the organization's identity administrator.
5. Verify the national carrier zones, tariff and serviceable PIN list with fulfillment. Review the initial delivery classifications assigned to historical packs and set individual fresh, dried and powdered SKUs explicitly wherever the legacy title was ambiguous. Course planning capacities are optional and should come from the training team.

### Visit analytics

Store owners can open **Visit analytics** at `/admin/analytics` for traffic sources, entry and last pages, shopping milestones, and a timeline of each visit. Filters support time range, shopping action, account name or email, and the displayed guest visit ID. The report treats 30 minutes without a recorded action as inactive. Payment submission and payment verification are separate steps.

Capture begins after the shopper allows analytics. A random tab visit can be linked to an authenticated customer account. Shoppers can turn analytics off in the storefront privacy settings. The collector stores allowlisted shopping paths and event details. Search text, form input, payment references, and raw referrer URLs are excluded.

The release migration creates two analytics tables. The authenticated daily cleanup in the deployment schedule removes visits and their events after 90 days of inactivity. Configure the scheduler with the existing `CRON_SECRET` and confirm its first successful run.

## Original audit

**Decision at the time of the audit.** I recommended holding that version. A catalog edit can reach a write handler without a staff permission check. Reading the public news page can initiate permanent deletion. The two payment desks can also leave staff and customers with different accounts of whether a payment was verified. These issues take priority over a visual refresh.

**Scope and confidence.** I mapped all 23 admin page definitions and 28 admin API route files covering 61 HTTP handlers. I followed the high-impact workflows into the shared catalog, order, payment, authentication and shipping code. Six actual page components ran in Chrome at 390 × 844 and 1440 × 900 with synthetic records, a simulated staff session and stubbed network responses. The five existing test suites for the inventory table, inventory arithmetic, workflow stepper, order statuses and invoice payment guard passed all 72 tests. These are component and source checks. The live local sign-in navigation timed out. An authenticated staging walkthrough, real bank reconciliation, production migrations and recovery, and performance under production volume still need verification. The audit used no customer records or production writes.

## Navigation, phones and accessibility

The first staff journey I would build is **Today → payment to check → order ready to pack**. The order reference, due amount, payment evidence, delivery method and next action should stay visible from one step to the next. A grower receiving stock should reach an adjustment directly from Today or Inventory. A trainer should reach a session roster without passing through store orders.

- **Navigation.** Use Today, Orders, Catalog & stock, Training, Marketing & content, and Settings & access. Keep badges for work that needs attention. Place shipping under fulfillment. Preserve the destination on sign-in and Back. The current wrapper always sends a signed-out operator to sign in with the dashboard as the return path. ## Maintainability and operations

1. **One staff entry point and a small permission matrix.** Protect the shared admin layout and each server operation. Standardize signed-out, forbidden, validation, conflict and retryable-failure responses. Start with the duties the team actually has. An owner can control access, fulfillment can move stock and dispatch, finance can reconcile payments, and editors can publish. Where one person wears several hats, grant them several duties. Verify revocation for an already signed-in staff member and strong authentication for owner/finance accounts. [Existing access helpers](../src/lib/admin.ts) · [OWASP authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)
2. **One transaction per business decision.** Keep the order stepper, pack conversion and invoice guard. Centralize the server transitions and reuse them from every applicable UI, job and webhook. Define one typed list/detail response per workflow. Reject stale edits with a reload-and-review action. Preserve purchase-time pack facts and a history of payment, stock, publication and access changes with actor, reason, record ID and time. Record only the data each workflow needs.
3. **Queries sized to the screen.** Paginate and filter in the database. Use count queries on Today, fetch detail only when opened, and remove review bodies and customer lists from dashboard traffic. Share URL-backed search, loading, empty, failure and retry behavior across queues. Measure the busiest queries with representative staging data before choosing additional indexes. [Admin product query](../src/app/api/admin/products/route.ts#L16) · [Dashboard requests](../src/app/admin/page.tsx#L34)
4. **Background jobs an operator can recover.** Record invoice, notification and import attempts, with status, retry count and a correlation ID. Show failed jobs to the owner, redact customer details and payment evidence from logs, and make a retry safe. Alert on the oldest pending payment and repeated invoice failures at thresholds the team agrees to. The current order handler starts post-transition work without waiting for durable completion. [Order side effects](../src/app/api/orders/%5Bid%5D/status/route.ts)
5. **A deploy and recovery procedure that can be rehearsed.** The build runs migrations and postbuild runs extra database scripts with a fallback that can mask failure. The existing additive reconciliation draft was rehearsed on disposable databases. It still needs production-schema comparison and adoption as a reviewed migration. Separate and visibly fail the migration step, rehearse a restore on a disposable copy, preserve legacy values, and have the operator reconcile counts before releasing. [Package scripts](../package.json) · [Existing reconciliation evidence and outstanding work](../audits/2026-11-24/migration/README.md)
